# Gap Implementation Roadmap

**Статус:** маршрут по находкам из [Gap Analysis](gap-analysis.md) и существующим Prototype Issues [#1–#11](https://github.com/tryproxy/tg-super-backend/issues?q=is%3Aissue+label%3Aprototype). Это планирование, а не новое принятое требование. Текущие требования находятся в [SPEC.md](../../SPEC.md), принятые объяснения — в [Decisions](../decisions.md).

## Как читать маршрут

**Gap перед Issue** — короткий шаг во время груминга этого Issue: решить спорное поведение, записать решение в SPEC/Decisions или оставить конкретный вопрос в [Open Questions](../open-questions.md), затем поправить критерии Issue. Код gap'а пишется **внутри следующего Issue**. После QA и закрытия Issue идём дальше по очереди. Отдельные GitHub Issues с label `gap` отслеживают G1–G6, но не входят в очередь реализации с label `prototype`. Закрываем их после выполнения условий в самих gap Issues и проверки соответствующих задач; отдельной ветки реализации gaps нет.

**Блокер** означает: не передавать указанный Issue в реализацию, пока его критерии противоречат принятому правилу или не описывают важный исход. Он не блокирует все более ранние Issues.

### Какое решение рекомендовано к шагу 7

Для Prototype предлагается хранить маршруты и статусы попыток, но не полные тексты переписки. При подтверждённом сбое публикации в топик сообщать об этом клиенту, если бот доступен. При неизвестном результате не отправлять то же содержимое автоматически: сообщить, что передача не подтверждена и может потребоваться повторить сообщение. Сбой самого уведомления тоже оставлять в безопасной диагностике. **Это рекомендация из Gap Analysis, а не уже принятое правило.**

Если нужен автоматический повтор исходного сообщения после потери webhook payload, потребуется временно хранить само содержимое и определить срок хранения и доступ к нему. Метаданные попытки не позволяют восстановить текст или файл. Существующий API для сверки неизвестного результата *создания топика* в #6 не превращается автоматически в API истории доставок: #9 сейчас исключает такой API.

## После Prototype

- **G7 — жизненный цикл интеграции:** перед задачами самостоятельной настройки в MVP решить, как отключать поддержку, менять токен, отключать Business и менять группу. Уточнить Open Questions, затем SPEC и MVP Issues.
- **G8 — доступ из Shell:** перед задачами Shell API в MVP закрыть Open Question 10 об ID продукта/remote и правах владельца на конкретную интеграцию.
- **G9 — «ожидает ответа» и агрегированные метрики:** возвращаться к ним только если после Prototype обнаружится потребность менеджеров. Сначала определить цель, затем создать User Story и Issue.
- Поиск по истории, полные тексты сообщений, AI-подсказки и API для других систем требуют отдельного продуктового решения. Их наличие в `web-chat-backend` не расширяет автоматически этот Prototype.

Расхождения в документах самого `web-chat-backend`, отмеченные в [Gap Analysis](gap-analysis.md), остаются предостережением при заимствовании его идей; это не дополнительные задачи Prototype.
